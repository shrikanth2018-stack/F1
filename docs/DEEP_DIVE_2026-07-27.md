## 1. Executive map

**The business.** A home-kitchen food + household-essentials delivery operation in Siddapur, Uttara
Kannada (single region, `Asia/Kolkata`). It sells meals and essentials on **fixed daily delivery
cycles** (Breakfast / Lunch / Snacks / Dinner), as one-off orders or **prepaid subscriptions**, with
last mile either **direct** (zone driver door-to-door) or **hub** (driver hands off at a hub, hub
operator does the last leg).

**One binary, four personas, routed by JWT claim.**

| Persona | Navigator | Entry |
|---|---|---|
| customer | `CustomerNavigator` | `RootNavigator.tsx:148` |
| staff (kitchen/packing) | `StaffNavigator` | `RootNavigator.tsx:147` |
| driver-staff | `CustomerNavigator` (keeps `role='staff'` for RLS) | `RootNavigator.tsx:142,148` |
| hub operator | `CustomerNavigator` + `assigned_hub_id` unlocks `HubDashboard` | `custom_access_token_hook.sql` claim |
| admin / super-admin | `AdminNavigator` | `RootNavigator.tsx:146` |

**Backend.** One Supabase project (`wcvqxzqqwcxlcgrjyunf`, no staging): Postgres with **45 tables**
(`src/types/database.types.ts`), RLS on every user-facing table, ~44 `SECURITY DEFINER` RPCs (only 30
appear in the generated types — see §2.8), **15 Deno edge functions**, `pg_cron` + `pg_net` for the
clockwork, Storage for assets, Auth with phone OTP and a custom access-token hook.

**The design centre — one sentence:** *the server decides money, dates and prices; the phone only
sends intent.* `supabase/functions/_shared/orderBuild.ts` is the single derivation both `quote-order`
(preview) and `place-order` (commit) call, so the quoted price and the charged price cannot diverge in
logic (`orderBuild.ts:1-21`).

**Data flow (order path).**

```
cart (Zustand)  →  quote-order  ─┐
                                 ├─ buildAuthoritativeOrder (_shared/orderBuild.ts)
Pay + client_quote → place-order ─┘        ↓
                                   drift check (integer paise)
                                          ↓  no drift
                            Razorpay order  |  atomic wallet debit
                                          ↓
                              place_order_atomic (1 tx, N cycle rows)
                                          ↓
              confirm-order (foreground)  ×  verify-payment (webhook, HMAC)
                                          ↓
                         status Confirmed → kitchen tick → staff board
```

## 4. Key journeys traced

### 4.1 Login → role routing

1. Splash held until the session check resolves; provider stack `ErrorBoundary → QueryClientProvider →
   AuthProvider → SafeAreaProvider → … → RootNavigator` (`App.tsx`).
2. `verifyOtp` → Supabase mints a JWT; `public.custom_access_token_hook`
   (`custom_access_token_hook.sql:52-96`) stamps `user_role`, `branch_id`, `assigned_hub_id`,
   `is_super_admin`, and a **derived** `is_driver` (true if the uid appears in
   `delivery_hubs.driver_user_id` or `delivery_zones.driver_user_id`, `:70-77`).
3. `extractRole` (`src/hooks/useAuth.ts:36-81`, now **exported** for tests) reads those claims with
   zero extra queries.
4. `RootNavigator.tsx:141-152` mounts the navigator. Driver-staff → `CustomerNavigator` while keeping
   `role='staff'` so RLS still grants order writes (`:142,148`).
5. New user (`step === 'name'`) → `OnboardingScreen` (`:116-135`) → `complete_onboarding_atomic`,
   which upserts the profile and inserts the first address in one transaction and derives `branch_id`
   from the zone/hub server-side (`complete_onboarding_atomic.sql`).

**Pricing arithmetic (`orderBuild.ts`).**
- Tax rate from `store_config.tax_rate_percentage` (`:124`); hard-fail → 503 (`:119-123`).
- **GST carve-out**: `inclusiveTax(gross) = round2(gross × rate / (100 + rate))` — `orderBuild.ts:127`.
- Applied **per group, to the item subtotal only** (`:255`, and `:346` for the subscription group) —
  i.e. **before** the delivery fee is added. The fee is untaxed.
- Group total = `subtotal + delivery_fee` (`:376`); tax is informational and never in the sum.
- Delivery fee is added **once**, to the earliest-dispatching group (`:364-373`); priority
  hub override → zone override → `store_config.delivery_fee` (`:152-162`).
- Grand total = Σ group totals (`:381`); drift tuple = `toPaise(grandTotal)` + sorted
  `(cycle_id, dispatch_date, group_total_paise)` (`:397-410`).

### 4.3 Customer essentials order

Structurally identical — a **separate** Zustand store (`essentialsCartStore.ts`) and separate smart-cart
hook, flowing into the same `quote-order`/`place-order` with `item_type: 'essential'`
(`orderBuild.ts:205-227`). `order_type` is derived server-side: `'food'` if any food item or food plan
is present, else `'essential'` (`orderBuild.ts:383-386`).

The essentials **gate is client-side only** — `useEssentialsEnabled()` reads

`CheckoutScreen.tsx:63-64`. **`orderBuild.ts` does not check it**: a hand-crafted `place-order` call
with essential item ids would still price and place. *(Low severity — the items are real and priced —
but it is a client-only rule on the money path.)*

### 4.4 Subscription lifecycle

- **Purchase** — one "subscription purchase" group, `cycle_id = null`, dispatched today, priced at
  `plan.price` (`orderBuild.ts:336-357`). Overlap conflict check: same `plan_type`, overlapping date
  range, shared `item_id` → 409 (`:310-334`); queued plans (non-overlapping) pass (`:323`).
- **Daily dispatch** — `generate_daily_manifest(p_target_date, p_cycle_id)`
  (`generate_daily_manifest.sql`): one `Confirmed` order per active, non-paused subscription; items
  mirrored from `subscription_plans.plan_items` JSON; **all money fields zero** (BF-19); idempotent per
  `(subscription_id, dispatch_date)`; per-subscription error isolation (O3) with a savepoint; best-effort
  push that can never roll back the meal; every run logged to `manifest_run_log`.
- **End of life** is driven by `days_consumed`, not the calendar — pause/skip/outage extend the plan;
  auto-deactivates when `days_consumed + 1 >= duration_days`.
- **New at HEAD**: `ux_orders_subscription_dispatch`, a partial unique index on
  `orders(subscription_id, dispatch_date)`, turns the previous `IF EXISTS`-only dedupe into a DB
  constraint (`log_retention_and_indexes.sql:102-104`).
- **Pause / skip / undo** — `usePauseSubscription`, `useSkipDay`, `useUndoSkip`.
- **Cancellation is admin-only** with prorated wallet refund (`admin_cancel_subscription_atomic`);
  `cancel-order` refuses subscription-purchase orders (guard G7).

### 4.5 Wallet top-up

`WalletScreen` → `useWalletTopup` → `wallet-topup` edge function: rate limit 5/60 s
(`wallet-topup/index.ts:60-70`), min/max from `store_config` (`:101-102`), **Razorpay REST order
created server-side** with a 15 s timeout (`:109-125`), `pending_wallet_topups` row inserted
(`:128-134`). It **never credits the wallet itself** (`:12-13`). Credit happens in
`complete_wallet_topup` via either `confirm-topup` (foreground) or `verify-payment`
(`verify-payment/index.ts:137-165`). Both idempotent.

### 4.6 Staff kitchen batch

1. `pg_cron` `kitchen-cutoff-push-tick` every minute → `trigger_kitchen_cutoff_pushes()`
   (`kitchen_cutoff_push.sql:200-247`). For each active cycle whose `kitchen_push_time` has passed IST,
   it derives the **delivery** date (cross-midnight → tomorrow, `:219-224`), dedupes against
   `kitchen_push_log(cycle_id, push_date)` (`:227-233`), then runs `generate_daily_manifest` for that
   cycle+date and `push_kitchen_summary`.
2. The push **is** the batch release. `useActiveStaffBatch` reads the latest `kitchen_push_log` row;
   `useStaffOrders` (`src/hooks/useStaffOrders.ts:52-101`) queries **that cycle + that date, excluding
   Cancelled** (`:73-75`) **OR** any past-dated non-terminal order (D2 carry-over, `:56-57`),
   branch-filtered (`:81-83`), hub-operator-filtered (`:94-98`), with subscription-purchase rows
   removed by `isOperationalOrder` (`:92`).
3. **An empty board before the day's first push is by design** (`useStaffOrders.ts:30-34`).
4. Kitchen tab renders `get_kitchen_aggregate` (`:172-185`) — server-side ingredient explosion.
5. Bulk advance = one `advance_orders_status` transaction (`:192-211`); only `Ready` fans a customer
   push server-side, `Packed` is deliberately silent (`advance_orders_status.sql:63-95`).

### 4.7 Driver / hub delivery + commission claim

- Persona gating in `src/utils/deliveryStatus.ts` (`nextDeliveryStatus(current, method, persona)`):
  driver on `hub` stops at `Received at Hub`; hub operator does `Received at Hub → On the Way →
  Delivered`; driver on `direct` does the full run; admin has the override.
- **Commission (new).** `get_hub_commission_summary()` (`hub_commission_claims.sql:74-131`) resolves
  the caller's `assigned_hub_id`, computes last month (claimable) and current month (accruing) via
  `_hub_commission_for_period`: base = `SUM(order_items.price_at_time × quantity)` over orders
  `Delivered` at that hub in the period with `item_type IN ('food','essential')` — which correctly
  values subscription dispatch deliveries despite their ₹0 order rows, and excludes subscription
  revenue rows (`:54-68`). Commission = `round(base × delivery_hubs.commission_percent / 100, 2)`.
- `create_hub_commission_claim()` (`:134-199`) re-computes server-side, refuses if

### 6.1 One enforcement gap worth your attention

**`place_order_atomic` appears to be executable by any authenticated user.**

*(Inference — schema.sql lags the live DB by the project's own rule. This needs a one-line check

## 8. Bulk-order groundwork

### 8.1 Order placement path

#### What `place-order` validates and computes

**Structural** (reusable by any order path — pricing, tax, dispatch, routing):

| Check | Where | Cycle-menu-specific? |
|---|---|---|
| Item exists and `is_active` | `orderBuild.ts:186-189, 212-215` | No |
| Item has a non-null `cycle_id` | `:190-192, 216-218` | **Item-level**, not menu-level |
| Cycle exists, is active, has `cutoff_time` + `delivery_start` | `:232-252` | No |
| Re-price from DB, ignore client price | `:196-200, 220-224` | No |
| Group by cycle | `:173-227` | No |
| Dispatch date A/B/C from server clock + cutoff | `:253,258` → `dispatch.ts:83-99` | No |
| GST carve-out per group | `:255,346` | No |
| Delivery fee once, on the earliest group, hub→zone→default | `:152-162, 364-373` | No |
| Address belongs to the user | `:142-148` (`.eq('user_id', userId)`) | No — **but user-scoped** |
| Serviceability | `:150`, enforced `place-order:152-154` | No |
| Storm mode | `:129-131`, enforced `place-order:149-151` | No |
| Subscription plan validity + overlap conflict | `:281-334` | No |
| Auth, rate limit, idempotency, drift, legacy-payload | `place-order/index.ts:76-170` | No |

**There is no cycle-menu constraint to relax.** This is the single most important finding for the
feature. A "menu" is not an entity — `menu_items` rows *are* the menu, each permanently tagged with
one `cycle_id`, and `orderBuild` never asks "is this item on today's menu for this cycle?" It only
asks "is this item active, and what cycle does it belong to?"

Consequences:
- **Already possible today:** ordering any active `menu_items` row, regardless of whether the customer
  UI currently surfaces it (the app filters by `is_active` and cycle, but the server does not gate on
  UI visibility).
- **Not possible today:** ordering an item **into a different cycle than the one it is tagged with**.
  The item's `cycle_id` *is* the group key (`orderBuild.ts:195,201`). "Any delivery cycle regardless of
  what that cycle's customer menu shows" therefore needs a **per-line cycle override**, not a relaxed
  validation.
- **Also not possible today:** ordering an inactive item. An admin path would need to decide whether
  `is_active` binds it.

**Not checked anywhere:** kitchen capacity (see §8.2), cycle cut-off as a *block* (see §8.2),
essentials module gate on the server (§4.3), any discount concept.

#### Could an admin-only server path reuse the logic without touching the customer path?

**Yes, and cleanly.** `buildAuthoritativeOrder` is a pure function over an injected client and an
injected clock, with no `auth.uid()` dependency — it takes `userId` as a parameter
(`orderBuild.ts:96-110`). It is already proven callable from two different endpoints. The natural
shape:

- A **new** edge function (`admin-place-order`) that authenticates the caller, checks
  `profiles.role = 'admin'` (the `elevate-employee/index.ts:54-60` pattern), and calls
  `buildAuthoritativeOrder` for the **target customer's** `userId`.
- **Do not add admin branches inside `place-order`.** Its rules block (`place-order/index.ts:10-22`)
  is a contract; every `if (isAdmin)` inside it is a new way to weaken the customer path by accident,
  and the payload-coupling rule means every change forces a joint app+function release.
- The two extension points `buildAuthoritativeOrder` needs to grow, both additive and both defaulted
  off, are: **per-line cycle override** and **discount**. Adding optional fields to `BuildArgs` leaves
  every existing caller byte-identical.
- Write path: `place_order_atomic` already accepts `p_user_id` explicitly and is used with the service
  role — it needs no change at all for an admin path. (It does need the grant fixed, §6.1.)

Where it attaches: the drift/idempotency machinery is orthogonal — see below.

#### Where GST is carved out, and where a discount must apply

Carve-out: `orderBuild.ts:127` —
`inclusiveTax(gross) = round2(gross × taxRate / (100 + taxRate))`, called at `:255` (item groups) and
`:346` (subscription group), each time on the **group subtotal before the delivery fee**.

For a 1–15% admin discount to leave the tax correct under GST-inclusive (T1) pricing, the discount must
reduce the **gross** and the tax must be recomputed from the discounted gross:

```
discountedSubtotal = round2(subtotal × (1 - d))
tax_amount         = inclusiveTax(discountedSubtotal)     // NOT the pre-discount tax
total_amount       = round2(discountedSubtotal + delivery_fee)
```

i.e. the discount belongs **between line 255 and line 256** of `orderBuild.ts` — applied to
`accum.subtotal` before `inclusiveTax` is called and before `group_total_paise` is computed at `:377`.
Applying it later (e.g. subtracting from `grand_total` at `:381`) would leave `tax_amount` reflecting a
price the customer never paid, and would corrupt the per-group `wallet_amount_used` split that
`place-order:221` derives from `g.total_amount`.

Two decisions that are yours, not the code's:
1. **Does the discount apply to the delivery fee?** Today the fee is untaxed and sits outside the
   subtotal, so discounting items only is both simpler and arithmetically cleaner.
2. **Per-group or per-order?** A single order can span cycles. A per-order percentage applied to each
   group's subtotal keeps every `orders` row self-describing (the property `mf10_place_order_atomic.sql`
   depends on: `SUM(orders.total_amount)` must stay correct for revenue reports).

There is **no discount column** on `orders` today. Recording the percentage would need either a new
nullable column or `orders.notes` (which `admin_cancel_order_atomic` already appends to — precedent
exists, but it is a string, not reportable).

#### Are idempotency and quote-drift reusable outside the customer flow?

**Idempotency: yes, directly.** `idempotency_keys` is keyed `(key, user_id, endpoint)` with the
endpoint as a plain string (`place-order/index.ts:94-102, 363-370`); `wallet-topup` already reuses the
same table with `endpoint = 'wallet-topup'`. An admin path uses `endpoint = 'admin-place-order'` and
gets replay protection for free. One caveat: it stores `user_id` — for an admin ordering *for* a
customer, you must decide whether the key is scoped to the **admin** (right answer: yes — it protects
against the admin's double-tap, which is the actual failure mode) or the customer.

**Rate limit: reusable but wrong as-is.** The 5/60 s counter reads the same table
(`place-order:82-91`). An admin doing bulk entry would trip it immediately. It should be either raised
or skipped for the admin path — a deliberate divergence, not an oversight to inherit.

**Drift: reusable but arguably unnecessary.** `driftedFields` (`dispatch.ts:128-152`) is a pure
function over `{total_paise, dispatches}` and works for any caller. But its purpose is *"the customer
was shown a number and must not be charged a different one."* In an admin flow with a payment link,
the price is fixed at link-creation time and the customer never sees a live quote. The honest design is:
**derive the quote once, freeze it into the payment link and the order rows, and skip the echo** — the
link's amount *is* the commitment. If you keep drift, you get a 409 on a stale admin screen, which for
bulk entry is friction rather than protection.

### 8.2 Order lifecycle and states

**Every status** (CHECK constraint, `orders_status_drop_paid.sql:14-19`):
`Pending`, `Confirmed`, `Preparing`, `Ready`, `Packed`, `Dispatched`, `Received at Hub`,
`On the Way`, `Delivered`, `Cancelled`, `Failed`. Flow order in `src/utils/orderStatus.ts:15-18`.
`'Paid'` was dropped as dead — **but `cancel-order/index.ts:34` still lists it in
`CANCELLABLE_STATUSES`**, harmlessly.

| Status | Set by | Reaches staff board? | `kitchen_push_log`? | Push? |
|---|---|---|---|---|
| `Pending` | `place-order:214` (razorpay) | Yes if in the pushed cycle (only `Cancelled` is excluded, `useStaffOrders.ts:74`) | counted in the summary | none |
| `Confirmed` | `place-order:214` (wallet); `confirm-order:130-135`; `mark_order_paid`; `generate_daily_manifest` | Yes | Yes | `order.confirmed` / `order.razorpay_confirmed` |
| `Preparing` | staff, `useUpdateOrderStatus` | Yes | — | **silent** |
| `Ready` | staff, incl. `advance_orders_status` | Yes | — | `order.ready` |
| `Packed` | staff | Yes | — | **silent by design** |
| `Dispatched` | staff/driver | Yes | — | `order.dispatched` |
| `Received at Hub` | driver (hub method) | Yes | — | `order.received_at_hub` |
| `On the Way` | hub op / driver | Yes | — | **silent** |
| `Delivered` | hub op / driver / admin | Drops out of carry-over | — | `order.delivered` |
| `Cancelled` | `cancel-order`, `admin_cancel_order_atomic` | Excluded | — | `order.cancelled` |
| `Failed` | `mark_order_failed` (webhook) | Drops out of carry-over | — | `order.payment_failed` |

**Is there a "created but unpaid" state?** Yes — **`Pending`**, and it is exactly the state an
admin/payment-link flow needs. What happens to a `Pending` order that is never paid:

- It **is never cleaned up**. Nothing sweeps stale `Pending` rows — no cron, no expiry.
- The customer sees a recovery banner for **2 hours only** (`useOrders.ts:105,113`), then it silently
  disappears from their home screen while the row lives on.
- **It is visible to the kitchen and counted in the kitchen summary** if its cycle pushes, because
  `useStaffOrders` excludes only `Cancelled` (`useStaffOrders.ts:74`) and `get_kitchen_aggregate`
  excludes only `Cancelled` (`get_kitchen_aggregate.sql:44`).

That last point is the sharpest constraint on the payment-link design: **"confirmed only when payment
is acknowledged" is not what `Pending` currently means operationally.** An unpaid admin order sitting
at `Pending` when its cycle pushes will be cooked. A payment-link flow needs either a genuinely new
pre-order status (a CHECK-constraint change, touching the staff queries, the offline replay guard in
`useOfflineSync`, and `ORDER_STATUS_FLOW`) or a rule that admin orders are not written to `orders`
until the payment webhook fires.

**Cycle cut-off enforcement.** The cutoff is *not* a block — it is a **date shifter**
(`dispatch.ts:83-92`). Ordering after the cutoff never fails; it moves the dispatch date to tomorrow
(B) or the day after (C). The only place a cutoff *blocks* anything is cancellation
(`cancel-order/index.ts:183-222`). So "any delivery cycle regardless of the menu" is already half-true
for timing: a late admin order simply lands on a later date. Placing an order onto a **past or
already-pushed** date is not possible through any existing path.

**Kitchen capacity: does not exist.** I searched the whole tree for capacity / max-orders /
daily-limit concepts and found none. There is no per-cycle cap, no ingredient stock check, no warning.
Bulk B2B orders will land on the kitchen with no guard rail whatsoever — the kitchen learns about a
200-portion order when the summary push arrives.

### 8.3 Payments

**What exists.**

- **In-app checkout SDK** — `react-native-razorpay` via `src/utils/razorpay.ts` /
  `razorpay.native.ts` (web shim). Opened at `CheckoutScreen.tsx:296-298`. Not available on web
  (`:174-181`).
- **Server-side Razorpay REST — yes, it already exists, in two places**:
  `place-order/index.ts:181-198` and `wallet-topup/index.ts:109-125`. Both `POST
  https://api.razorpay.com/v1/orders` with HTTP Basic auth
  (`btoa(KEY_ID:KEY_SECRET)`), `AbortSignal.timeout(15_000)`, and a shallow error check
  (`if (!rzpOrder.id) return 502`). Keys come from `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` in the
  function env.
- **No shared HTTP helper.** The two call sites are copy-paste. There is no retry, no structured
  error mapping, no logging of the Razorpay response beyond the 502 body.
- **Signature verification** — `hmacSha256Hex` via Web Crypto, duplicated verbatim in
  `verify-payment/index.ts:29-40`, `confirm-order/index.ts:28-39`, and `confirm-topup`. Two different
  signing payloads: the webhook signs the **raw request body** (`verify-payment:66`); the foreground
  path signs `razorpay_order_id|razorpay_payment_id` (`confirm-order:113-116`).
- **Webhook handling** — `verify-payment` handles `payment.captured`, `order.paid`, `payment.failed`,
  and **acks any unhandled event type with 200** (`:270-272`) so Razorpay stops retrying.
- **Idempotency on repeat webhook delivery** — real and layered: `mark_order_paid` is status-guarded;
  `complete_wallet_topup` is status-guarded; subscription activation filters `.eq('is_active', false)`
  (`:174-175`). All three branches run every time and no-op when nothing matches (`:92-97`). Errors are
  logged but return **200** deliberately, to avoid infinite Razorpay retries (`:106-108`).

**What does not exist — and this is genuinely new ground.**

- **Razorpay Payment Links are a different API** (`POST /v1/payment_links`) and none of the existing
  code touches them. They are not `orders`; they carry their own `plink_*` id.
- **They fire different webhook events** — `payment_link.paid`, `payment_link.expired`,
  `payment_link.cancelled` — none of which `verify-payment` handles. Today those events hit line 270
  and get acked with `ok: unhandled` while nothing happens. A payment-link flow needs the Razorpay
  dashboard webhook subscription extended **and** new branches in `verify-payment`.
- Note that a captured payment-link payment *does* also produce a `payment.captured` event whose
  `payload.payment.entity.order_id` is the auto-created order id — so `verify-payment` would see it
  but find no matching row and log "No matching order/topup/subscription" (`:207-209`). *(Inference on
  Razorpay's exact payload; verify against their docs before designing on it.)*
- **No customer-facing link delivery mechanism**: no SMS provider integration exists anywhere in the
  repo. Razorpay can send the link itself (`notify: {sms, email}`), which is the cheapest path.
- **No `orders` column for a payment-link id.** `razorpay_order_id` is a text column and could hold a
  `plink_*` id, but every existing lookup (`mark_order_paid`, `mark_order_failed`,
  `confirm-order:133`, the three webhook branches) matches on it, so overloading it needs care.

**Wallet ↔ order payment.** Mutually exclusive today: `payment_method` is `'wallet'` or `'razorpay'`
(`place-order:124-126`). Wallet debits the full `grand_total` atomically before the write
(`:203-211`), splits per-row as `g.total_amount` (`:221`), and refunds automatically on write failure
(`:239-269`). **There is no partial/split payment** — no "wallet + card". Cancellation refunds only the
wallet portion; the Razorpay portion becomes `razorpay_refund_due` for a manual dashboard refund
(`cancel-order:153,286`).

### 8.4 Users and auth

**How a user is created today — every row written.**

1. `supabase.auth.verifyOtp` (or `auth.admin.createUser`) inserts into **`auth.users`**.
2. The `on_auth_user_created` AFTER INSERT trigger fires `handle_new_user()`
   (`handle_new_user.sql:6-16`), inserting a **stub `public.profiles` row**:
   `(id, role='customer', phone_number = NEW.phone)` with `ON CONFLICT (id) DO NOTHING` and
   **NULL `branch_id`**. Phone is stored **without the leading `+`** — `91XXXXXXXXXX`.
3. `complete_onboarding_atomic` upserts `full_name` + derived `branch_id` onto that profile and inserts
   the **first `customer_addresses` row** (`is_default = TRUE`), both in one transaction, deriving
   `branch_id` from `delivery_zones.branch_id` → `delivery_hubs.branch_id` → `1`.
4. Optionally `apply-referral` writes a `referrals` row, sets `profiles.referred_by`, and credits the
   signup wallet bonus.

**The JWT role claim depends on** `profiles.role`, `profiles.branch_id`, `profiles.assigned_hub_id`,
`profiles.is_super_admin`, plus a live `EXISTS` over `delivery_hubs.driver_user_id` /
`delivery_zones.driver_user_id` for `is_driver` — all read by `custom_access_token_hook`
**at token mint time**. A profile change only reaches the app on the next token refresh (the app
proactively refreshes on foreground, `useAuth.ts:124-131`).

**Does an admin/service-role path already create users? Yes — `elevate-employee` is the template.**
`supabase/functions/elevate-employee/index.ts`:
- Admin gate by reading `profiles.role` with the service-role client (`:54-60`), plus a super-admin
  gate for `ADMIN HEAD` (`:78-81`).
- Phone normalisation: strip non-digits, take the last 10, build `e164 = '+91' + ten` and
  `phoneStored = '91' + ten` (`:83-87`). **This normalisation is exactly what a bulk-order customer
  creation needs, and its comment at `:117-123` explains why the stored form matters.**
- **Find-or-create**: `auth_user_id_by_phone(phoneStored)` SECURITY DEFINER RPC first — because the
  `auth` schema is not exposed via PostgREST (`:89-100`) — then
  `adminClient.auth.admin.createUser({ phone: e164, phone_confirm: true, user_metadata })` (`:105-114`).
- Then the atomic profile RPC.

**For creating a customer from the admin side, the pieces you'd use:**

| Need | Existing piece |
|---|---|
| Look up an existing user by phone | `auth_user_id_by_phone` RPC (SECURITY DEFINER, `REVOKE ALL FROM PUBLIC`) |
| Create the auth user | `auth.admin.createUser({phone, phone_confirm: true})` — service role only |
| Profile row | created automatically by the `handle_new_user` trigger, `role='customer'` |
| Set the name / branch | `profiles_admin_all` RLS already permits a branch admin to update, or a new atomic RPC mirroring `complete_onboarding_atomic` |
| Create the address | `addresses_self` RLS **already permits** a branch admin to insert for another user (`rls_policies.sql:227-233`) |
| Resolve serviceability | `resolve_address_serviceability(lat, lng)` — SECURITY DEFINER, returns zone/hub/serviceable |

**Caveat:** `complete_onboarding_atomic` cannot be reused as-is — it hard-blocks on
`auth.uid() IS DISTINCT FROM p_user_id` (its own defence-in-depth guard). An admin equivalent would be
a sibling RPC with an `is_admin()` gate instead. A bulk-created customer whose address is created by an
admin will *not* get a `phone_confirm` OTP flow — they log in normally later and their profile is
already populated.

**Phone OTP configuration.** The app calls `supabase.auth.signInWithOtp` / `verifyOtp`
(`useAuth.ts:151-164`); the SMS provider is configured entirely in the Supabase dashboard
(Authentication → Providers → Phone). **The provider and account owner are not recorded anywhere in
the repo** — `docs/07-incident-playbooks.md:120` explicitly flags this as an open item with blank
fields. If MSG91 is intended for both OTP and confirmations, note that Supabase's phone provider list
is fixed (Twilio, MessageBird, Vonage, Textlocal) — **MSG91 would be a separate integration for the
confirmation SMS, not a swap of the OTP provider.** *(Inference on Supabase's supported list;
verify in the dashboard.)*

**Addresses and geolocation.** `customer_addresses` holds `latitude`/`longitude` (numeric),
`address_line`, `landmark`, `city`, `pincode`, `label`, `full_name`, `phone_number`, plus the
server-resolved `zone_id`, `hub_id`, `branch_id`, `is_serviceable`. Resolution is
`point_in_polygon` ray-casting against `polygon_geojson` arrays of `{lat,lng}`
(`serviceability_server_side.sql:16-58`), wrapped by `resolve_address_serviceability` which returns
`'unknown'` when nothing is configured so setup never blocks ordering. `hub_id` on the address decides
`delivery_method` at order time (`orderBuild.ts:163`). **An order attaches to an address by
`delivery_address_id`, and `orderBuild` scopes the lookup to `.eq('user_id', userId)`
(`orderBuild.ts:142-147`)** — so an admin path must pass the *customer's* userId, not the admin's.
There is no address validation beyond the polygon test — no pincode check, no geocoding of typed text.

### 8.5 Menu model

**How items compose.** A `menu_items` row is a whole sellable thing ("Breakfast Thali") with a
`name`, GST-inclusive `price`, a mandatory `cycle_id`, `is_active`, `sort_order`, and an
`ingredients` **text** column holding its components. `CreateMenuScreen` collects `{name, qty}` pairs
and stores them (`CreateMenuScreen.tsx:32,86-92`).

**Components are not entities.** They have no id, no price, no row, no `is_active`. They exist only as
text inside their parent's `ingredients` column. `order_items.item_id` references a `menu_items` (or
`essentials_catalog`) id.

**Can an individual component be ordered on its own today? No.** There is nothing to reference. What
blocks it, concretely:
- No id → `order_items.item_id` has nothing to point at.
- No price → `orderBuild.ts:196-200` re-prices from `menu_items.price`; a component has none.
- No cycle → `orderBuild.ts:190-192` hard-fails an item with a null `cycle_id`.
- `get_kitchen_aggregate` explodes parents *into* components; a component ordered directly would need
  the fallback path (`get_kitchen_aggregate.sql:50-56`).

The two honest routes are (a) create each sellable component as its own `menu_items` row — zero code
change, but it pollutes the customer menu unless you add a "not customer-visible" flag; or (b) promote
components to a real table with ids and prices — a much larger change that touches the kitchen
aggregation, the plan `plan_items` JSON, CSV import, and the admin menu builder.

**⚠️ Two incompatible `ingredients` formats are live.**

| Writer | Format |
|---|---|
| `CreateMenuScreen.tsx:91` | `JSON.stringify([{name, qty}])` |
| `ImportItemsScreen.tsx:196` ← `csvParsers.ts:99-103` | plain text, e.g. `"Idli:2"` |
| `MenuManageScreen.tsx:39-49` (reader) | tries `JSON.parse`, **falls back to showing the raw string** |
| `get_kitchen_aggregate.sql:57-66` (reader) | splits on `;`, then on `:` — **plain text only** |

A menu created through the in-app builder produces JSON that the kitchen aggregator will split on `;`
(no match), yielding one "component" named `[{"name"` with token `"Idli","qty":"2"}]` — garbage in the
Kitchen tab. CSV-imported items work correctly. `MenuManageScreen` renders both, so the problem is
invisible from the admin side. **This is a real bug at HEAD, unrelated to the bulk feature but sitting
in exactly the code any component-level ordering would touch.**

**Cycle→menu mapping** is `menu_items.cycle_id` (and `essentials_catalog.cycle_id`,
`subscription_plans.cycle_id`). Everything that reads it: `useMenuItems`, `useAllMenuItems`,
`useEssentialsCatalog`, `useSubscriptionPlans`, `HomeScreen` grouping, `CartScreen` grouping,
`orderBuild.ts:195,201,219,225`, `get_kitchen_aggregate.sql:41`, `generate_daily_manifest.sql`
(`sp.cycle_id` selects which subscriptions a tick dispatches), `MenuManageScreen`,
`EssentialsCatalogManageScreen`, `PlansManageScreen`, `CreateMenu`/`CreateEssential`/`CreatePlan`.

### 8.6 Admin surface

**Manage tab structure.** A flat `SettingsRow` list grouped by section header, defined in two places
that must be kept in sync: the `ManageRowDef[]` array (`AdminHome.tsx:166-188`, used for the search
filter) and the rendered JSX (`:243-307`). Super-admin-only rows are gated by
`bf.isSuperAdmin` (`AdminHome.tsx:169-170`, `BranchRow` at `:58`).

**The established pattern for a new admin screen:**
1. Create `src/screens/admin/<Name>Screen.tsx`.
2. Add the route to `AdminStackParamList` (`src/navigation/types.ts`).
3. Register it in `AdminNavigator.tsx` under the right comment block.
4. Add the row to **both** the `MANAGE_ROWS` array and the JSX in `AdminHome.tsx`.
5. Role gating: the navigator does not gate — `AdminNavigator` is only mounted when
   `session.role === 'admin'` (`RootNavigator.tsx:146`). Finer gating is done *inside* the screen
   (`BranchesManageScreen` "gated on `is_super_admin` both server-side and at the entrance") or at the
   row (`AdminHome.tsx:169-170`).

**Existing admin write paths that bypass the customer flow**, and what they leave behind:

| Path | Mechanism | Audit trail |
|---|---|---|
| `admin_cancel_order_atomic` | SECURITY DEFINER + `is_admin()` + `FOR UPDATE` lock + status guards | **appends** `[Admin cancel: reason]` to `orders.notes`; wallet ledger row via `increment_wallet_balance` |
| `admin_cancel_subscription_atomic` | same shape | prorated wallet credit row |
| `elevate-employee` | edge function, service role, admin gate | `profiles` + `staff_salary` first row; no dedicated log |
| `advance_orders_status` | SECURITY DEFINER + staff/admin role check | `orders.updated_at`; pushes logged to `push_logs` |
| `print_supply_batch_atomic` | SECURITY DEFINER + `is_admin()` | `supply_batches` snapshot row |
| Custom push composer | `send-push` with admin JWT | every attempt in `push_logs` with `trigger_source='admin_custom'` |
| Direct table writes (menu, plans, cycles, zones, hubs, flags, config) | plain PostgREST under branch-scoped admin RLS | **none** — no audit table exists for config changes |

**The pattern to copy for bulk order entry** is `admin_cancel_order_atomic`: SECURITY DEFINER, explicit
`is_admin()` at entry, `REVOKE ALL FROM PUBLIC` + `GRANT EXECUTE TO authenticated`, row locks where
concurrency matters, and an append-only trace on the row. For anything that computes money, the newer
`create_hub_commission_claim` is the better template — it shows the current house style for
"server computes the amount, client sends nothing" (`hub_commission_claims.sql:134-199`).

**There is no general audit log.** If admin-placed orders need to be distinguishable from customer
orders — for reports, for accountability, for the B2B/bulk split — that has to be designed in (a
column on `orders`, or a `placed_by` uuid), because nothing today records who created a row.

## 10. Open questions for you

**Blocking-ish for the bulk feature**

1. **The `place_order_atomic` grant (§6.1).** Please run
   `SELECT proname, proacl FROM pg_proc WHERE proname IN ('place_order_atomic','order_items');`
   in the SQL editor. If `authenticated` has EXECUTE, that is a free-food hole and should be fixed
   before any new order path is built on top of it.
2. **What does "confirmed only when payment is acknowledged" mean operationally?** A `Pending` order
   today *is* visible to the kitchen and counted in the summary (§8.2). Do you want (a) a genuinely new
   pre-order status that the staff board ignores, or (b) admin orders that don't touch `orders` at all
   until the webhook fires? These are very different amounts of work.
3. **Individual components:** are the components you want to sell a *small, fixed* set (→ make each one
   a `menu_items` row with a "hide from customer menu" flag, near-zero code) or *any* component of any
   menu (→ promote components to a real table, large change)?
4. **"Any delivery cycle regardless of the menu"** — do you mean (a) *any active item, even one the
   customer UI doesn't currently show* (already possible server-side), or (b) *this item, delivered on
   that other cycle's run* (needs a per-line cycle override that no code path has today)?
5. **Discount recording** — is a percentage on the order enough for reports, or do you need the
   discount value carried per line? The first needs one nullable column; the second changes
   `order_items`.
6. **MSG91 + DLT** — is MSG91 also intended to replace the Supabase phone-OTP provider, or only to send
   the confirmation SMS? Related: **who owns the current OTP SMS provider account?**
